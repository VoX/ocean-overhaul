# Ocean Overhaul — feature audit & deficiency list

_Generated 2026-06-09 from a 9-agent ultracode per-feature review of branch `auto/overnight-2026-06-09`. Read-only audit; nothing was changed. For owner review._

## Verdict

Ocean Overhaul is feature-complete and genuinely survival-usable: across 6 audit areas (boss, mobs, combat gear, armor, worldgen/trench, aquarium/bucketing, blocks/food/materials) every registered feature is wired with complete, non-placeholder assets (verified against docs/renders contact sheets and per-recipe images), 64 of 68 items and all 36 blocks have a traced survival acquisition path, and 46/46 gametests pass with zero failures or errors. The only true creative-only ids are the 4 spawn eggs, which is correct vanilla behavior since all 4 mobs spawn naturally (and the 2 fish are bucket-capturable). There is exactly ONE functional, player-visible defect — the Deep-Sea Helmet refreshes NIGHT_VISION to 60 ticks, permanently below MC's 200-tick steady threshold, so a submerged wearer gets constant strobing instead of clean night vision (verified at OceanOverhaul.java:1061 + refreshEffect at :1083). Everything else is proof-coverage gaps (behaviors that work but aren't gametested or screenshotted), owner's-call balance/discoverability notes, two doc/log mismatches, and a salt-block storage asymmetry. Verdict: ship-ready as a feature-complete mod; fix the one night-vision line, and the rest is QA-proof hardening the operator should gather, not blocking bugs.

## Operator-verified top issues (tinyclaw)

I hand-verified the load-bearing findings against the source. Two are genuine functional bugs that block intended survival play — fix these before release:

1. **[HIGH — survival-blocking] Trench reward blocks don't drop when mined.** `abyssal_vent` and `giant_clam` are `AbstractBlock.Settings.copy(Blocks.PRISMARINE)` (OceanOverhaul.java:302/309), which carries `requiresTool=true`, but neither is in `data/minecraft/tags/block/mineable/pickaxe.json`. With a tool required and **no** mineable tag, no tool is ever "correct" → mining them (even with a pickaxe) drops **nothing**. So the Giant Clam's guaranteed-Abyssal-Pearl reward — the whole point of finding the trench — is **unobtainable in survival**, and Abyssal Vent can't be collected at all. (The audit ranked this LOW as a "missing pickaxe tag / slow mining" note; it's actually a no-drop. `glowing_plankton_block` copies SEA_LANTERN, no tool required, so it's fine.) **Fix:** add `oceanoverhaul:abyssal_vent` + `oceanoverhaul:giant_clam` to `mineable/pickaxe` (one-line data edit).

2. **[MEDIUM — degraded UX] Deep-Sea Helmet night-vision strobes underwater** (see #1 below) — the 60-tick refresh sits permanently under MC's 200-tick steady threshold, so a submerged wearer gets constant flashing instead of steady vision. One-line fix (duration > 200).

Other real (non-proof) items: **Salt Block** is a one-way storage block (9 sea_salt in, 1 back via smelting, no unpack recipe — loses 8/9; see #6); **in-world trench worldgen is unproven** (every gametest bypasses biome attachment, so nothing confirms the BiomeModifications actually places features in a live deep-ocean chunk — wiring looks correct but the failure mode is total; see #2); two **doc/log mismatches** (README reef-fish "cod", load-log "45 blocks/30 items"; see #13). Everything else below is proof-coverage hardening (behaviors that work but lack a gametest/screenshot) and owner's-call balance/discoverability notes — not blockers.

Nothing was changed — this is for your review. Say the word and I'll fix the two functional bugs (both are one-liners) + backfill the proof gaps.

## Deficiencies (ranked, from the audit synthesis)

### #1 — [MEDIUM] Diving Kit — Deep-Sea Helmet (Night Vision when submerged)
- **Issue:** OceanOverhaul.java:1061 calls refreshEffect(player, NIGHT_VISION, 60, 25). refreshEffect (:1083-1090) only re-applies when remaining duration < reapplyBelow, so the applied duration cycles 60->25->60 ticks and is PERMANENTLY under Minecraft's 200-tick steady-render threshold. The client (GameRenderer.getNightVisionStrength) pulses/fades night vision below 200 ticks, so a submerged wearer sees constant strobing the entire time underwater instead of steady vision. This is the only functional, player-visible defect in the whole mod.
- **Survival impact:** A survival player who crafts and wears the Deep-Sea Helmet (a headline Diving Kit feature, craftable from abyssal_pearl + glass_pane) gets a flickering/strobing screen while diving rather than clean night vision — degraded, potentially nausea-inducing UX. The effect technically applies, so it is not unusable, but it does not work as intended.
- **Suggested fix:** Raise the applied duration comfortably above 200 ticks while keeping the submerged gate, e.g. refreshEffect(player, NIGHT_VISION, 300, 220) — applies 15s, refreshes under 11s, always >200 so steady, and clears within a few seconds of surfacing. Exact steady duration is owner's call; invariant is duration > 200 at all times while worn. PROOF: divingkitgametest.divingpiecesgranttheireffectswhenworn only asserts hasStatusEffect(NIGHT_VISION)==true so it PASSES despite the flicker; gametests cannot see render strength — needs a submerged-wearer client screenshot to expose the strobe (before) and confirm steady vision (after).

### #2 — [MEDIUM] BiomeModifications wiring / all three trench features

All worldgen gametests (featuresResolveFromRegistry, planktonPatchActuallyPlaces, newBlocksPlaceBreakDrop) use EMPTY_STRUCTURE + a direct ConfiguredFeature.generate() call (WorldgenGameTest.java:131, caveat at :52-56), which bypasses Minecraft's biome-attachment placement entirely. - **Survival impact:** If the attachment silently failed (a biome-tag or step mismatch that still compiles), the ENTIRE trench would be invisible in survival — no plankton, no vents, no clams, no guaranteed pearls — i.e. registered-but-unreachable content. Wiring looks correct so live risk is low, but the failure mode is total and currently unverified by any test or screenshot.
- **Suggested fix:** Operator should do one in-world confirmation pass: generate a fresh world, /locate biome minecraft:deep_ocean, fly the floor and confirm glowing plankton (common), an abyssal vent (rarity 6), and a giant clam (rarity 8) actually generate; capture a natural-gen screenshot to replace biome-hero.png. PROOF: build/gametest/report.xml worldgengametest.* all pass but bypass biome attach (WorldgenGameTest.java:52-56 caveat); biome-hero.png is a scene, not natural-gen proof.

### #3 — [MEDIUM] Aquarium break-drops (onStateReplaced bucket scatter)
- **Issue:** The onStateReplaced scatter of a stored creature's filled bucket on break is not gametested. AquariumGameTest.aquariumPlaceAndBreakLifecycle places an EMPTY tank, breaks it, and only asserts the BlockEntity is gone (confirmed: setStored is used only in the unrelated NBT/store/retrieve tests, not the break lifecycle). So the 'don't silently void the captured creature' guarantee, including correct variant on the scattered jelly bucket, is untested against AquariumBlock.onStateReplaced.
- **Survival impact:** If a regression broke the scatter (wrong key check, scatter ordered after super, or wrong rebuilt bucket), a survival player who mines an occupied aquarium would permanently lose the captured fish/jelly with no warning. The code is currently correct, so impact today is nil — this is a high-value missing test on a destructive-loss path.
- **Suggested fix:** Add a gametest that stocks a BE (e.g. setStored(JELLYFISH, 3)), sets the block to AIR, and asserts a Bucket of Jellyfish ItemEntity with Variant==3 spawned at the position (and that a previously-empty tank scatters nothing). PROOF: AquariumGameTest.aquariumPlaceAndBreakLifecycle (empty-only) is the partial proof; code under test is AquariumBlock.onStateReplaced (lines ~136-146).

### #4 — [MEDIUM] Multipart MegalodonSegment hitbox chain (damage forwarding)
- **Issue:** The core 'the boss body is hittable' mechanic has no gametest. MegalodonSegment.damage (verified at lines 56-61: if source.getAttacker()!=null && owner!=null && owner.isAlive() -> owner.damage) forwards a player/projectile hit on an invisible segment to the shark. The 5 segments ARE the real player-facing hitbox (the shark's own EntityType box is intentionally tiny ~1.6 wide), yet only segment COUNT (isPartOf filter) is tested, never the damage path, and never the attacker-null environmental guard.
- **Survival impact:** If segment damage-forwarding or the attacker-null guard regressed, a survival player could swing at the visible shark body and deal zero damage, making the boss effectively unkillable — with no test to catch it. The wiring is correct today.
- **Suggested fix:** Add a gametest: spawn boss, tick until segments exist, deal a known attacker-bearing DamageSource to a segment, assert boss.getHealth() dropped by the amount; also assert an attacker-less DamageSource on a segment does NOT reduce boss health (the lava/void guard). PROOF: megalodongametest.megalodonspawnsfivehitboxsegments covers count via isPartOf; a damage-forward test would prove the body is hittable.

### #6 — [LOW] Salt Block storage round-trip
